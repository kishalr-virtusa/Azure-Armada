# Tech stack and why (judge Q&A prep)

Team Azure Armada · Disaster Recovery (DR) Agent: Autonomous Disaster Recovery Validation

Use this to answer "what did you use, why this, why not that". Every answer is about what we actually built.

## The one-line architecture
Six AI agents on **Azure AI Foundry Agent Service** decide and explain; a **guarded engine** in the DR console executes
only allowlisted Azure actions from a validated, human-approved plan; it fails a real workload over from
**East Asia to Southeast Asia** and measures RTO/RPO from evidence.

## Decisions

| Layer | We chose | Why | Why not the alternative |
|---|---|---|---|
| Agent platform | **Azure AI Foundry Agent Service** (6 versioned prompt agents, strict JSON output schemas) | Azure-native agent hosting: agents are visible and versioned in the Foundry portal, use Entra/managed identity, and each has a contract (output schema) we validate | **Semantic Kernel / AutoGen / LangChain**: orchestration frameworks we don't need, because our orchestration is a deterministic engine by design. **Direct Azure OpenAI calls**: kept only as the automatic fallback |
| Models | **gpt-4.1-mini** for Architect, Readiness, Runbook, Reporter; **gpt-5-mini (reasoning)** for Planner and Validator | Fast and cheap with reliable structured outputs for summarising; reasoning where it matters (multi-step plans, diagnosing failures with evidence) | **GPT-4o**: retired. **Bigger models**: slower and pricier with no quality gain on our measured tasks (Validator answers in ~7s, Planner ~30s) |
| Agent safety | **"Agents decide, the engine acts"**: allowlisted actions, mandatory safe sequence, plan validation (human 'go' before the outage and before failback enforced by the engine; stale commands refused), human approval gates, kill switch, rollback, deterministic fallback per agent | DR touches production: every action must be predictable, auditable and reversible. A model can never call an Azure write API | **Giving the LLM write tools (function calling that changes Azure)**: one hallucinated tool call could fail over production. Agents get read-only tools only (next row); writes stay in the engine's 15 allowlisted actions |
| Agent tools | **Read-only tools via Foundry function calling** for the Validator and Readiness agents: `probe` (region or Traffic Manager), `traffic_manager`, `web_app`, `sql_failover_group`, `app_settings_diff`, `site_recovery`. Per-agent tool allowlist; `tool_choice=required` on the first round when something is wrong; every call shown in the live activity panel | The agent investigates the way an engineer would (e.g. calls `app_settings_diff()` and finds PAYMENT_PROVIDER only in East Asia) instead of judging a summary we pre-chewed. Read-only means a wrong tool call costs a few seconds, never an outage. `tool_choice=required` stops the model from answering from the prompt alone when evidence is available | **Write tools for agents**: unsafe in DR (see above). **No tools, only a prepared summary**: the agent cannot dig further than what code anticipated |
| Autonomy | **Autopilot**: runs the 7 readiness checks every 10 min with no one asking; on a new failure the Readiness agent investigates with its tools and explains; levels **Observe**, **Propose fixes** (default: fix waits for human approval), **Auto-fix config drift** (only the allowlisted DR-side fix: copy a missing app setting to Southeast Asia, audited). Never runs during a drill, never starts drills or touches traffic | Drift happens between drills; a check nobody runs finds nothing. Autonomy is bounded by the same allowlist as everything else, and the only automatic fix touches the DR side, never the primary or traffic | **Autopilot that starts drills or reroutes traffic**: a production-impacting action without a human. **Production note**: the loop runs inside the console today; in production we would move it to an **Azure Functions timer trigger** so it does not depend on the console being up |
| Load testing | **"Under payment load" drill mode**: 20 confirmed database writes per second from parallel writers, every write checked after the failover | One write a second can hide replication lag; at 20/s the forced failover shows real loss (19 Oct: RPO 1.95 s, 15 of 466 acknowledged writes lost; another load drill RPO 1.84 s, 13 of 156) | Azure Load Testing / JMeter: measures throughput, not which acknowledged writes survived |
| Demo-week tier | **App Service Premium P0v3 + SQL Standard S1** for demo week (about $6.75/day), reverted after with `infra/scripts/demo-tier.sh down` | Faster restarts: failback 1 min 43 s – 2 min 55 s (was 3 min 44 s on B1); a config fix takes effect in ~30 s (was ~80 s); headroom for load mode | Staying on B1 + SQL Basic: works, but slower failback; staying on Premium permanently: needless cost on a $200 credit |
| Output reliability | **Strict JSON schemas** + server-side validation (e.g. the Architect's recommendation is checked against the numbers) | No free-text parsing; wrong answers are rejected and retried. We found and fixed a case where the model claimed a strategy met targets it didn't | Free-text answers: unparseable and unverifiable |
| App + console hosting | **Azure App Service (Linux, Python 3.11)** | Simplest managed PaaS with zip deploy, managed identity, health checks, start/stop APIs (used to inject the outage). The workload itself is PaaS, so DR of App Service is the realistic scenario | **AKS**: cost and ops overhead for 3 small apps. **Functions**: our engine is a long-running drill thread (minutes) with in-process state. **Container Apps**: viable, but App Service gave us start/stop and slots semantics directly |
| Web framework | **FastAPI** + server-rendered Jinja + small vanilla JS | Typed, async, fast to build; no front-end build pipeline to break before a demo; Azure SDKs are first-class in Python | **React SPA**: a build step and more moving parts for no user benefit here |
| Database | **Azure SQL (Basic; Standard S1 in demo week) + auto-failover group** | Payments are relational; a failover group gives one listener name, forced (disaster) and planned (no data loss) failover, and replication lag we can read | **Cosmos DB multi-region**: different consistency model, higher cost, not the classic enterprise DR case judges recognise |
| Global routing | **Azure Traffic Manager** (priority routing, /health probes every 10s, TTL 10s) | DNS-level failover between regions with health probes; the engine flips endpoints and follows TM's routing decision | **Azure Front Door**: forbidden on Free Trial ("Free Trial and Student account is forbidden for Azure Frontdoor resources"). **Application Gateway**: regional, not cross-region |
| IaaS DR | **Azure Site Recovery (A2A)** with **test failover** into an isolated network | The standard Azure VM DR service; test failover proves recovery without touching production; we verify by running a command inside the recovered VM | **Azure Backup restore**: recovery in hours, not minutes; no non-disruptive drill |
| VM OS | **Windows Server 2022 Core** | The ASR Linux agent supports only specific kernel builds; current Ubuntu kernels were rejected in both regions we tried | Linux: replication failed on kernel compatibility |
| Regions | **East Asia (A) ↔ Southeast Asia (B)**, console in **South India** | An official Azure paired region; the control plane sits outside both so it survives the disaster it manages | Indian pairs: Central India throttled App Service creation on our subscription; South/West India rejected new Azure SQL servers |
| Drill state | **Azure Storage Tables + Blob** | Serverless, cheap, durable; the engine resumes a drill after a console restart | Cosmos/SQL for state: unnecessary cost and coupling to the database we fail over |
| Secrets + identity | **Key Vault + managed identities** for Azure access (no keys in code); the database login is a Key Vault secret; Entra ID sign-in built (needs tenant consent) | Zero secrets in the repo (scanned); Azure RBAC limited to the DR resource groups | App settings with plain secrets. Next step for production: Entra-only SQL auth with managed identity and private endpoints |
| Measurement | **Heartbeat writer** (one confirmed DB write every second, or 20 per second from parallel writers in load mode) for RPO; RTO = outage injected until the first healthy check through Traffic Manager from Southeast Asia (engine checks every second) | Evidence-based, not estimated: every write the database acknowledged until the forced failover *completed* (including during it) must exist in the new primary; RTO is split into measured segments that add up exactly | Reading replication lag alone: it estimates, it doesn't prove |
| Notifications | Live console alerts (instant) + **Azure Monitor action group** email (audit trail) | Azure-native and works on Free Trial | Azure Communication Services email: blocked on Free Trial. Google Chat/Gmail: blocked by the tenant |
| Infrastructure as code | **Bicep** + `up.sh` / `down.sh` (one command each) | Azure-native, supports new resource types on day one (Foundry projects), no state file to manage | **Terraform**: great tool, but a state backend to manage and slower support for brand-new Azure APIs |
| Chaos | Our own **engine-controlled fault** (disable the DR traffic endpoint mid-failover), armed by the presenter | Tests the exact failure an operator could cause, and ties into the Validator + human-approved fix | **Azure Chaos Studio**: roadmap; our fault needs to be coordinated with the drill engine |
| UI design | `docs/design/DESIGN.md` from awesome-design-md (Vercel discipline + Virtusa accent; Mercury for Contoso) | A written design system keeps every screen consistent | Ad-hoc styling: looks AI-generated |

## Likely follow-up questions
- **Is the outage real?** We simulate the loss of the region by stopping the app tier and forcing the database failover; everything after that (rerouting, recovery, measurement) is real.
- **Zero downtime?** No: about 30–40 s of disruption (RTO 27.74–40.43 s across 10 completed drills), against a 30-minute target, and a forced failover loses the last couple of seconds of writes (RPO 1.84–2.80 s in our write-by-write drills). Zero downtime and zero loss need active-active / synchronous replication at much higher cost.
- **What if the AI is wrong?** It cannot act. The engine rejects plans that break the safe sequence, numbers are verified by code, humans approve risky steps, and every agent has a rules-based fallback.
- **What does it cost?** $2.44 in total for the first two days of building and 9 drills, 17–18 Oct (Azure Cost Management, actual bill in US$). All AI agent calls together in that period: $0.09. The PaaS DR pair runs at $38.26/month at list prices. Demo week adds the Premium tier, about $6.75/day, reverted after the demo.
- **How do you scale this to many apps?** Each app gets a profile (RTO/RPO, tier); the agents and the allowlisted actions are generic per service type (App Service, SQL, Traffic Manager, ASR). New service types = new allowlisted actions.
- **Is 35 s what a real user sees?** It is the time until a fresh lookup of the Traffic Manager name plus a health check succeed from Southeast Asia, as seen by the console. Phones in the demo reconnect through `/pay`, which does the same fresh lookup. A browser that cached DNS longer (TTL is 10 s) or stays on the old hostname could take a little longer; that is client behaviour, not recovery time.
- **You said RPO 0 earlier. Why is it 2 s now?** The earlier "RPO 0" came from a narrower method; our own audit found it. Now RPO is proven write by write: every write the database acknowledged until the forced failover *completed* (including during it) must exist in the new primary. Results: 19 Oct, no load, RPO 2.80 s (2 of 45 lost); under payment load (20 writes/s) RPO 1.84 s (13 of 156) and 1.95 s (15 of 466). That is what a forced failover with asynchronous replication does; the target is 15 minutes.
- **Why do the agents call tools, and why only read-only ones?** So they can investigate instead of guessing from a summary, and so a bad tool call can never change anything. Writes stay in the engine (15 allowlisted actions) behind human approvals. `tool_choice=required` forces at least one tool call when something is wrong, so every diagnosis rests on live evidence, and every call is shown in the activity panel.
- **Is Autopilot safe? What can it do on its own?** It runs the 7 readiness checks every 10 minutes and explains new failures. By default it only *proposes* a fix and waits for a human. In Auto-fix mode it applies only one allowlisted, DR-side fix (copy a missing app setting to Southeast Asia), audited. It never runs during a drill, never starts a drill and never touches traffic. Real example: on 19 Oct a scheduled check found PAYMENT_PROVIDER missing in Southeast Asia (HTTP 503) with no human trigger. In production we would run the loop on an Azure Functions timer instead of inside the console.
- **Why Premium for the demo?** Speed, not correctness: on P0v3 failback took 1 min 43 s – 2 min 55 s (3 min 44 s on B1) and a config fix takes effect in ~30 s (~80 s on B1). About $6.75/day; `infra/scripts/demo-tier.sh down` reverts it after the demo.
- **Can the AI start an outage or skip an approval?** No. The engine rejects any plan where a region-changing action is not exactly where the safe sequence puts it, or where a human approval is missing before the outage or before failback. Approvals and commands are only accepted for the step that is actually waiting.
